❯ Why would a recursive function that calls itself be so slow for n = 3501

⏺ A self-calling version would look like this:

  def legpoly_rec(n, x):
      if n == 0: return 1.0
      if n == 1: return x
      return ((2*n-1)*x*legpoly_rec(n-1, x) - (n-1)*legpoly_rec(n-2, x)) / n

  This is the same recursion, shifted down by one so that it computes Pₙ from
  Pₙ₋₁ and Pₙ₋₂. It is correct, but it is very slow, for two reasons.

  1. It repeats the same work. Each call makes two more calls. Follow
  legpoly_rec(5):

  P5 → P4, P3
  P4 → P3, P2        ← P3 again
  P3 → P2, P1        ← P2 again (and P3 itself appears twice, so all of this
  doubles)

  Nothing remembers a result, so P₃, P₂ and the rest get recomputed over and
  over. The number of calls grows like the Fibonacci numbers, roughly 1.6ⁿ:

  ┌──────┬─────────────────┐
  │  n   │ calls (approx.) │
  ├──────┼─────────────────┤
  │ 10   │ ~180            │
  ├──────┼─────────────────┤
  │ 30   │ ~2.7 million    │
  ├──────┼─────────────────┤
  │ 50   │ ~40 billion     │
  ├──────┼─────────────────┤
  │ 3501 │ ~10⁷³¹          │
  └──────┴─────────────────┘

  Already at n = 50 it would take minutes to hours. At n = 3501 it would never
  finish: 10⁷³¹ is vastly more than the number of atoms in the universe, about
  10⁸⁰.

  2. Python limits how deep calls can nest. Python allows about 1000 nested
  calls by default. legpoly_rec(3501) has to go 3501 levels deep before it
  reaches P₁, so it would crash with a RecursionError before even getting to the
  slowness.

  Why your loop doesn't have this problem: it works upward from P₀ and P₁. Each
  Pₖ is computed exactly once, and p_prev and p_curr keep only the two values
  the next step needs. So for n = 3501 it does about 3500 steps, taking a
  fraction of a millisecond, with no nesting at all. The docstring's line "This
  is the only efficient way to calculate values of Legendre polynomials of high
  degree" refers to exactly this.

  Check your understanding: roughly how many loop passes does your legpoly(50,
  x) do, compared with ~40 billion calls for the recursive version? And which
  single feature of the loop avoids all that repeated work?

  If you want to see this for yourself, put legpoly_rec in a scratch file (not
  legendre.py) and time n = 25 against n = 30. Predict how much slower 30 will
  be before you run it.

❯ what does print(..., end='')

⏺ By default, print adds a newline ('\n') after whatever it prints, so the next
  print starts on a new line. The end argument changes what gets added at the
  end. end='' means "add nothing," so the next print carries on on the same
  line.

  print("a")
  print("b")
  prints
  a
  b

  print("a", end='')
  print("b")
  prints
  ab

  You can make end any string you like:

  print("a", end=' ')     # a space
  print("b", end=' | ')   # a separator
  print("c")
  prints
  a b | c

  Why it's useful in loops: you can build up one row of output a piece at a
  time.

  for j in range(1, 4):
      print(j, end=' ')
  print()          # an empty print() just outputs '\n', ending the row
  prints
  1 2 3

  Predict: what does this print, line by line?
